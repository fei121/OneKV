# Qwen2.5-3B — 4-Way N-Scale Comparison (N=3…10)

Same ToolBench-style ReAct trace, `N` concurrent agents, **12 sessions**, tool_wait 200 ms,
RTX 3090 (24 GB, CUDA 12.8). Backends: **llama.cpp** (llama-server, slot-pinned),
**vLLM**, **SGLang**, **shared-KV engine** (single-engine continuous batching + prefix caching).
vLLM / SGLang measured with **per-token streaming** so TPOT is a true per-token p95.

## Key findings

- **Throughput scales with N and is far ahead of every baseline.** The engine goes
  **165.3 → 351.6 tok/s** (N=3→10), a ~2.1× gain, and is 137–152% above vLLM/SGLang and
  3–10× above llama.cpp. llama.cpp does not scale (peaks at 113.7 at N=6, degrades to 75.5
  at N=9, recovers to 93.4 at N=10; N=3 here is the fresh 12-session baseline).
- **Decode latency is essentially load-independent for the engine.** Engine TPOT p95 stays in the
  narrow band **12.5–15.4 ms** across all N, while **llama.cpp degrades monotonically**
  33.8 → 104.4 ms by N=8 and then **125.9 ms at N=10**. Under concurrency the engine's
  continuous-batching decode path is never starved — this is the AgentServe decode-protection
  benefit, reproduced across the full N range.
- **vLLM and SGLang are also only mildly load-sensitive** (TPOT p95 12–28 ms), but they cap at
  ~175–258 tok/s. The engine's prefix-cached shared prefill + packed decode round gives more
  headroom.
- **N=10 needs the full 24 GB**: the engine run used `n_ctx=65536` to hold the shared system prefix
  (≈2700 tokens) for 10 sessions plus the decode KV; it completed with `total_decode=1383` and no
  OOM.
- **llama.cpp at N=10 needs a larger context than the default.** The baseline config uses
  `context_length=24576`, so `--parallel 10` gives only ~2457 tokens/slot — smaller than the
  2693-token cold prompt, so every slot overflowed and llama-server emitted **0 tokens**
  (the earlier N=10 row was empty). Re-running with `context_length=49152` (~4915 tokens/slot)
  produces the real N=10 point above (93.4 tok/s, TPOT p95 125.9 ms).

## Reproduction

- Engine values come from `scripts/run_engine.sh` (single-engine shared-KV runtime) + the engine
  `[engine] DONE` summary line and per-token event logs.
- Baselines run per-N via `scripts/serve_llama.py` / `scripts/serve_backend.py --backend {vllm,sglang}`
  (see `scripts/README.md`). vLLM/SGLang use `--stream-interval 1` for true per-token TPOT.
  llama.cpp N=10 uses a model config with `context_length=49152` (see `configs/models/qwen25_3b_n10.yaml`).
- Raw per-N metrics: `metrics/nscale-4way/{engine_summary.csv,engine_N*.jsonl,{llama,vllm,sglang}_N*.json}`.
- Figure regenerated by `scripts/plot_4way_nscale.py`.

## Session-level SLO attainment

SLO attainment rate (fraction of sessions meeting both `TTFT ≤ τ_TTFT` and `TPOT p95 ≤ τ_TPOT`,
with τ from an isolated N=1 profile ×2.0 = 744 ms / 20.3 ms) is reported separately —
see [`4way-nscale-slo.md`](4way-nscale-slo.md) and
[`figures/4way-nscale-slo.png`](../figures/4way-nscale-slo.png). Highlight: the shared-KV engine
maintains **100% SLO attainment at every N**, while llama.cpp drops to ~0% from N=4.
